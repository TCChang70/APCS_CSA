### Question 1 — Immutable class design

Which is **not** a requirement for designing an immutable class?

A. Declare all fields `private` and `final`  
B. Do not provide setter methods that modify fields  
C. Declare the class `final` or make constructors `private`  
D. Provide a public no-arg constructor  
E. If the class holds mutable objects, do not expose them directly

<details>
<summary>Answer</summary>
**D. Provide a public no-arg constructor**

A no-arg constructor is not required for immutability. In fact, an immutable class typically requires all field values to be provided via the constructor.
</details>

### Question 2 — Defensive copy

```java
import java.util.*;

public final class SecurePerson {
    private final String name;
    private final List<String> tags;

    public SecurePerson(String name, List<String> tags) {
        this.name = name;
        this.tags = tags;  // line 1
    }

    public List<String> getTags() {
        return tags;  // line 2
    }
}
```

Which security problem exists in this class?

A. The class is not declared `final`  
B. The caller can modify `tags` after construction through the reference stored at line 1  
C. The `name` field should not be `final`  
D. The class cannot be subclassed  
E. No security problem — the class is properly immutable

<details>
<summary>Answer</summary>
**B. The caller can modify `tags` after construction through the reference stored at line 1**

A mutable `List` is passed by reference. Both the caller and the object hold the same reference. The caller can modify the list after construction, breaking immutability. The fix is to make a defensive copy: `this.tags = new ArrayList<>(tags)`.
</details>

### Question 3 — Input validation

```java
public class Calculator {
    public int divide(int a, int b) {
        return a / b;
    }
}
```

What is the most appropriate security improvement?

A. Make the method `synchronized`  
B. Validate that `b` is not zero before division  
C. Change the return type to `double`  
D. Declare the method as `final`  
E. Catch `ArithmeticException` and return `-1`

<details>
<summary>Answer</summary>
**B. Validate that `b` is not zero before division**

Input validation is a key security practice. Checking `b != 0` prevents `ArithmeticException`. Catching the exception after the fact (E) is less proactive.
</details>

### Question 4 — Sensitive data exposure

```java
import java.io.*;

public class User implements Serializable {
    public String username;
    public transient String password;
}
```

Which statement about this class is true from a security perspective?

A. `transient` prevents the password from being serialized, improving security  
B. `transient` has no effect on serialization  
C. The `password` field will be serialized as `null` and cannot be recovered  
D. Both fields are serialized normally  
E. The class cannot be serialized because of `transient`

<details>
<summary>Answer</summary>
**A. `transient` prevents the password from being serialized, improving security**

The `transient` keyword prevents the field from being serialized, so the password will not be written to the output stream. This is a common practice for sensitive data like passwords.
</details>

### Question 5 — Unmodifiable collections

```java
import java.util.*;

public class Test {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>(List.of("A", "B", "C"));
        List<String> unmod = Collections.unmodifiableList(list);
        list.add("D");
        System.out.println(unmod.size());
    }
}
```

What is the result?

A. `3`  
B. `4`  
C. An `UnsupportedOperationException` is thrown  
D. Compilation fails  
E. The program prints nothing

<details>
<summary>Answer</summary>
**B. `4`**

`Collections.unmodifiableList()` returns a view backed by the original list. The view prevents direct modification through `unmod`, but changes to the underlying `list` are reflected. This can be a security concern — the "unmodifiable" list can still change.
</details>

### Question 6 — Preventing class extension

Which modifier is used to prevent a class from being subclassed?

A. `abstract`  
B. `final`  
C. `private`  
D. `static`  
E. `sealed`

<details>
<summary>Answer</summary>
**B. `final`**

A `final` class cannot be extended. This is often used for security to prevent malicious subclassing that could override methods.
</details>

### Question 7 — Minimum privilege principle

Which practice best follows the principle of least privilege?

A. Declare all methods as `public` for maximum flexibility  
B. Use the most restrictive access modifier that still allows the code to work  
C. Always use `protected` so subclasses can override  
D. Make all fields `public` to avoid getter/setter overhead  
E. Use package-private access by default for all members

<details>
<summary>Answer</summary>
**B. Use the most restrictive access modifier that still allows the code to work**

Least privilege means code should only have the access it absolutely needs. Start with `private` and open up access only when necessary.
</details>

### Question 8 — Preventing denial of service (DoS)

Which practice helps prevent denial of service attacks in Java?

A. Using unlimited collection sizes for user input  
B. Validating and limiting input size before processing  
C. Making all classes `final`  
D. Using `StringBuilder` instead of `String` for concatenation  
E. Declaring all variables as `var`

<details>
<summary>Answer</summary>
**B. Validating and limiting input size before processing**

Without input size validation, an attacker could send enormous inputs to exhaust memory or CPU, causing a denial of service.
</details>

### Question 9 — Secure object construction

```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {
        if (INSTANCE != null) {
            throw new RuntimeException("Cannot reflectively create instance");
        }
    }

    public static Singleton getInstance() {
        return INSTANCE;
    }
}
```

What attack does the constructor check prevent?

A. SQL injection  
B. Reflection-based instantiation via `setAccessible(true)`  
C. Serialization attacks  
D. Thread-safety issues  
E. Cross-site scripting

<details>
<summary>Answer</summary>
**B. Reflection-based instantiation via `setAccessible(true)`**

Even with a `private` constructor, reflection can bypass the access check using `Constructor.setAccessible(true)`. The check inside the constructor detects this by checking if `INSTANCE` is already set.
</details>

### Question 10 — Preventing integer overflow

```java
public class Test {
    public static int addPositive(int a, int b) {
        if (a <= 0 || b <= 0) {
            throw new IllegalArgumentException("Only positive values allowed");
        }
        return a + b;
    }

    public static void main(String[] args) {
        System.out.println(addPositive(Integer.MAX_VALUE, 1));
    }
}
```

What is the result?

A. `2147483648`  
B. `-2147483648` (integer overflow)  
C. `Integer.MAX_VALUE + 1`  
D. An `IllegalArgumentException` is thrown  
E. An `ArithmeticException` is thrown

<details>
<summary>Answer</summary>
**B. `-2147483648` (integer overflow)**

The check ensures inputs are positive but does not check for overflow. `Integer.MAX_VALUE + 1` wraps to `Integer.MIN_VALUE`. The fix is `Math.addExact(a, b)` which throws `ArithmeticException` on overflow.
</details>
