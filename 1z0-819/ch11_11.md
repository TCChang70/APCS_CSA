### Question 1 — SQL injection prevention

Which JDBC approach prevents SQL injection attacks?

A. Using `Statement` with string concatenation for parameters  
B. Using `PreparedStatement` with `?` placeholders  
C. Using `Statement.executeQuery()` instead of `execute()`  
D. Using `DriverManager.getConnection()` with encrypted credentials  
E. Using `ResultSet.getObject()` instead of `getString()`

<details>
<summary>Answer</summary>
**B. Using `PreparedStatement` with `?` placeholders**

`PreparedStatement` uses parameterized queries, which separate SQL logic from data. User input is treated as data only, preventing SQL injection. String concatenation with `Statement` (A) is vulnerable.
</details>

### Question 2 — execute(), executeUpdate(), executeQuery()

```java
import java.sql.*;

public class Test {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:derby:testdb";
        try (Connection cn = DriverManager.getConnection(url);
             Statement st = cn.createStatement()) {

            String sql1 = "CREATE TABLE items (id INT, name VARCHAR(50))";
            boolean r1 = st.execute(sql1);
            System.out.print(r1 + " ");

            String sql2 = "INSERT INTO items VALUES (1, 'Pen')";
            boolean r2 = st.execute(sql2);
            System.out.print(r2 + " ");

            String sql3 = "SELECT * FROM items";
            boolean r3 = st.execute(sql3);
            System.out.print(r3);
        }
    }
}
```

Assuming the table is created successfully, what is the result?

A. `false false true`  
B. `true true true`  
C. `false false false`  
D. `true false true`  
E. `false true false`

<details>
<summary>Answer</summary>
**A. `false false true`**

`Statement.execute()` returns `false` for DDL (`CREATE TABLE`) and DML (`INSERT`), and `true` for queries (`SELECT`) that produce a `ResultSet`.
</details>

### Question 3 — ResultSet next() loop

```java
import java.sql.*;

public class Test {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:derby:testdb";
        try (Connection cn = DriverManager.getConnection(url);
             Statement st = cn.createStatement();
             ResultSet rs = st.executeQuery("SELECT * FROM users")) {

            while (rs.next()) {
                System.out.print(rs.getString("name") + " ");
            }

            // Attempt to iterate again
            while (rs.next()) {
                System.out.print(rs.getString("name") + " ");
            }
        }
    }
}
```

What happens during the second `while (rs.next())` loop?

A. The same results are printed again  
B. No output — the cursor is already past the last row  
C. A `SQLException` is thrown  
D. Compilation fails  
E. The results are printed in reverse order

<details>
<summary>Answer</summary>
**B. No output — the cursor is already past the last row**

`ResultSet` cursor moves forward only (by default). After the first loop, the cursor is positioned after the last row. The second `rs.next()` immediately returns `false`.
</details>

### Question 4 — Transaction commit/rollback

```java
import java.sql.*;

public class Test {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:derby:testdb";
        try (Connection cn = DriverManager.getConnection(url)) {
            cn.setAutoCommit(false);
            try (Statement st = cn.createStatement()) {
                st.executeUpdate("INSERT INTO accounts VALUES (1, 100)");
                st.executeUpdate("INSERT INTO accounts VALUES (2, 200)");
                cn.commit();
            } catch (SQLException e) {
                cn.rollback();
            }
        }
    }
}
```

If the first `INSERT` succeeds but the second `INSERT` fails, what is the state of the database?

A. Both rows are inserted  
B. Only the first row is inserted  
C. Neither row is inserted  
D. An exception is thrown but the first row remains  
E. Compilation fails

<details>
<summary>Answer</summary>
**C. Neither row is inserted**

With `autoCommit(false)`, the transaction is managed manually. If any exception occurs, `cn.rollback()` undoes all changes in the transaction, ensuring atomicity — either all changes succeed or none do.
</details>

### Question 5 — PreparedStatement reuse

```java
import java.sql.*;

public class Test {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:derby:testdb";
        String sql = "INSERT INTO items VALUES (?, ?)";
        try (Connection cn = DriverManager.getConnection(url);
             PreparedStatement ps = cn.prepareStatement(sql)) {

            ps.setInt(1, 1);
            ps.setString(2, "Item A");
            ps.executeUpdate();

            ps.setInt(1, 2);
            ps.setString(2, "Item B");
            ps.executeUpdate();
        }
    }
}
```

What is the advantage of reusing the `PreparedStatement` with different parameters?

A. Only the last set of parameters is inserted  
B. The SQL is parsed once, improving performance for multiple executions  
C. It prevents the use of parameterized queries  
D. It requires calling `clearParameters()` between each execution  
E. It automatically commits each insert

<details>
<summary>Answer</summary>
**B. The SQL is parsed once, improving performance for multiple executions**

`PreparedStatement` precompiles the SQL. When reused with different parameters, the database does not need to re-parse and re-optimize the SQL statement, improving performance for batch-like operations.
</details>

### Question 6 — Batch updates

```java
import java.sql.*;

public class Test {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:derby:testdb";
        try (Connection cn = DriverManager.getConnection(url);
             PreparedStatement ps = cn.prepareStatement(
                 "INSERT INTO items VALUES (?, ?)")) {

            ps.setInt(1, 1);
            ps.setString(2, "A");
            ps.addBatch();

            ps.setInt(1, 2);
            ps.setString(2, "B");
            ps.addBatch();

            int[] results = ps.executeBatch();
            System.out.println(results.length);
        }
    }
}
```

What is the result?

A. `1`  
B. `2`  
C. `0`  
D. An exception is thrown  
E. Compilation fails

<details>
<summary>Answer</summary>
**B. `2`**

`addBatch()` adds the current set of parameters to the batch. `executeBatch()` executes all accumulated statements and returns an `int[]` with one element per operation. Two inserts were batched → length is 2.
</details>

### Question 7 — ResultSet column index vs name

```java
import java.sql.*;

public class Test {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:derby:testdb";
        try (Connection cn = DriverManager.getConnection(url);
             Statement st = cn.createStatement();
             ResultSet rs = st.executeQuery("SELECT id, name FROM users")) {

            while (rs.next()) {
                System.out.print(rs.getInt(1) + " ");
                System.out.print(rs.getString(2) + " ");
            }
        }
    }
}
```

Which statement about column access by index is true?

A. Column indices start at `0`  
B. Column indices start at `1`  
C. Column indices start at `1` for `getInt()` but `0` for `getString()`  
D. Column access by name is faster than by index  
E. Column indices must match the order in the database schema

<details>
<summary>Answer</summary>
**B. Column indices start at `1`**

JDBC column indices are 1-based. `getInt(1)` retrieves the first column (`id`), `getString(2)` retrieves the second column (`name`). Access by index is generally faster than by name.
</details>

### Question 8 — DataSource vs DriverManager

Which statement about `DataSource` compared to `DriverManager` is true?

A. `DataSource` always requires a JDBC URL  
B. `DataSource` provides connection pooling capabilities  
C. `DriverManager` is part of `javax.sql` package  
D. `DataSource` is only available for MySQL databases  
E. `DriverManager` supports JNDI lookups

<details>
<summary>Answer</summary>
**B. `DataSource` provides connection pooling capabilities**

`DataSource` (from `javax.sql`) supports connection pooling and distributed transactions. `DriverManager` (from `java.sql`) is a simpler, basic connection factory. `DataSource` objects can be registered with JNDI.
</details>
